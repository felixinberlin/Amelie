# Constraint Release — What Changed?

Find an ambition that could help people and explain precisely why a verified change makes a previously blocked experiment worth trying. Work in both directions: blocker → change, and change → affected blockers. Unlike bisociation, require a causal before/after argument rather than a distant analogy; unlike inversion, do not require reversing a system.

## 0. Read memory and set a budget

Read `AGENTS.md`, the last retro in `06-suche/amelie-constraint-release-log.md`, the current playbook/atlas and `08-friedhof/README.md`. Run `npm run bib -- find --stamm <terms>`; inspect matching candidates, Dosen, graves and their exact resurrection conditions. Read the underlying evidence, not only the summary. Use the source register through read-only `quellen next` / `show`.

Inspect at most three blocker/change pairs per run and perform at most four targeted external searches per pair (recipient, functional prior art, international tools, technical bridge). Prefer the strongest pair; allow zero survivors. Respect the Vertex prohibition and the assigned tool/time budget. Do not buy services, launch paid provider runs or contact recipients.

## 1. Make a blocker ledger

Describe an evidenced ambition, beneficiary and observable benefit. Separate every necessary blocker: availability, license/permission, measurement validity, accuracy, cost/latency, maintenance, adoption and actual need. Record the old evidence/date, threshold for removal and exact grave condition when applicable.

A missing problem is not a technical blocker. A built tool is not revived just because a new algorithm exists. Treat `never` resurrection conditions as binding: report unchanged scope as blocked. A materially different scope may be investigated as a linked hypothesis; do not rewrite the original grave or pretend its cause was removed.

## 2. Verify a delta

Read dated primary evidence for the claimed change. Record publication date separately from effective availability and compare with the old evidence. A 2025 dataset does not establish a change since a September 2026 rejection; it may correct earlier knowledge, but label it as newly discovered evidence, not a new capability.

Distinguish discovery, implementation, accessible/reusable artifact and measured improvement. Label claims `[Seite]`, `[Schnipsel]`, `[Local file]` or `[Hypothesis]` according to actual reading. Stored research is secondary evidence; never claim to have freshly verified its external sources. If access fails, leave the delta unknown and specify the exact retrieval needed.

## 3. Test the causal bridge

Write: old constraint → specific changed fact → mechanism → testable improvement. Give units, scale, required inputs and operational assumptions.

Ask the counterfactual: could the same experiment have worked without this change? If yes, describe an ordinary baseline or knowledge correction rather than a breakthrough-enabled opportunity. Consult `mathematician` for theorem/algorithm assumptions when available, otherwise follow its skill directly. Separate theorem validity, application fit and empirical benefit. An asymptotic bound, shared vocabulary or impressive benchmark does not provide an executable method for this input.

Assign a change assessment: `removed`, `partial`, `unchanged`, or `unknown`. This is NOT an Amélie existence verdict. A surviving downstream blocker keeps overall feasibility unresolved even when one constraint is removed.

## 4. Recheck need and prior art independently

Check the intended institutional recipient first, then functional German/English searches and research/open-source implementations. Compare the exact scope and cheaper existing workflow. Preserve the usual existence verdicts (`frei`, `verengt`, `unklar`, `besetzt`); when verification is incomplete use `unklar`. Do not equate a constraint assessment with novelty, a reviewer score or packing permission.

Keep negative results in the engine log. Only send a candidate to review when there is a documented need and a causal bridge or a clearly labeled bounded research question. Reuse existing Dosen as modules where appropriate. Do not create speculative duplicates or repeated graves.

## 5. Design one decisive experiment

Specify input provenance/license, baseline, held-out evaluation if applicable, metric, provisional pass threshold, stop/falsification condition, time/compute budget and remaining blocker. Declare whether target-site history is allowed: a fully withheld station cannot supply climatology, thresholds or tuning data; use training-only donor-station baselines instead. Freeze thresholds before running; label them research triage criteria, not safety/policy guarantees. Synthetic tests validate mechanics only. Do not infer rescued birds, accessibility gains or happier lives without an outcome measurement.

## 6. Return and log

Return one card per inspected pair:

- Original ambition / memory ID and scope; people helped.
- Old blocker, evidence/date, removal threshold and resurrection condition.
- Changed fact, primary source/date, availability and evidence quality.
- Causal bridge and counterfactual; change assessment.
- Every remaining blocker; prior art and separate existence verdict.
- Smallest experiment: baseline, metric, pass/stop criteria, budget.
- Route: review candidate, research task, existing-Dose module, or stop.

Append a run section only to `06-suche/amelie-constraint-release-log.md`, with learned / mistake / next time and Quellenmeldung. In CLI mode return the report; the runner appends it only with `--write`. Shared protocol, source register and grave updates belong to the librarian through the existing CLI. Preserve grave history and cite old IDs in any recheck.

For the existing CLI `candidates` contract, encode the full evidence chain in `quelle` and `beleg`, and the experiment plus remaining blockers in `restluecke`; keep them self-contained because reviewer/librarian handoffs select these fields. Put only review/research candidates in `candidates`; keep stopped pairs in the prose report. Return `candidates: []` when nothing qualifies. Include `gelernt`, `naechstesMal`, and valid `quellenmeldung` rows (values: `npm run -s bib -- quellen formate`). No invented source IDs or invented citations.
